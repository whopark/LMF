## 1. Executive Summary

| 관점 | 내용 |
|------|------|
| **Problem** | 연 1회 개정 시즌에 심사위원 30~50명이 공통문항 전파 누락, 수정사유 유실, 잠금 우회 등 데이터 정합성 리스크를 안고 수기·이메일 병행으로 작업한다. 현행 시스템은 검색 비활성, 화면 A→B 연동 불안정, Export 한글 미검증 등 신뢰 저하 요인이 남아 있다. |
| **Solution** | KSLM 심사점검표 도메인 모델(공통문항 last-6 키, C/R/B 분류, 분야특이 설명, 상태머신)을 시스템에 내재화한 개정 전용 워크플로우. 화면 A(개정대상 선정) → 화면 B(전후 비교·수정) → 검토중 → 최종 Lock → REVISED 태그 → Export를 단일 흐름으로 제공한다. |
| **Function·UX Effect** | 수정유형 복수선택 UI, 수정사유 verbatim 저장·표시, 공통문항 일괄 전파 모달, 분야별 워크리스트, 색상 강조 DiffText, Excel/Word/PDF 다운로드로 편집자·심사위원·마스터 권한자가 각자의 역할에 맞는 화면에서 동시에 작업할 수 있다. |
| **Core Value** | "공식본 = 시스템본" — KSLM 심사점검표 정합성 자동 보장, 수정이력 완전 추적, 인증갱신 증빙 PDF·Word·Excel 일괄 산출로 수기 병행을 제거한다. |

**현재 구현 상태 (2026-06-14 기준)**: Phase 4~7 완료. 개정 모델·상태머신·권한 분기·Export 라우트·프론트 RevisionPanel/DiffText/SideBySideItem/HistoryView가 코드베이스에 존재함. 아래 §5에서 갭 항목을 별도 표기함.

## 2. 배경 (Background)

### 2.1 왜 지금인가

- **연 1회 고정 개정 사이클**: 심사점검표는 매년 개정되며, 인증기관은 개정 완료 결과물을 공식 증빙으로 제출한다. 개정 시즌(약 2~3개월)에 오류가 발생하면 다음 인증 주기까지 수정 기회가 없다.
- **대안 부재**: 한국 KSLM 구조(공통문항, 분야특이 설명, C/R/B 배점 분류)를 지원하는 외부 시스템이 없다. CAP Checklist는 영문·미국 구조이며, 수기·엑셀은 버전관리·이력 추적이 불가능하다.
- **TFT 워크숍 결과(2026-06-09)**: 1차 전산 TFT 6개 기관 위원이 §3~§8의 개선 요구사항을 통합 확정했다. 이 PRD는 그 결과물을 제품 관점으로 공식화한다.

### 2.2 무엇이 바뀌었나

- Phase 4~7 구현으로 기본 골격이 완성되었으나, 수정사유 raw/display 분리, 화면 A 선택 서버 영속화, unlock 감사로그 강제, 분야별 Export ZIP 등 핵심 신뢰 보장 항목이 갭으로 남아 있다.
- 코드레벨 보안 리뷰(Phase 1~6 이슈 해소 커밋 후에도)에서 NoSQL 연산자 인젝션, TOCTOU 잠금 체크, API-key admin fallback 등 재발 가능 패턴이 확인되었다.

## 3. 시장 세그먼트 및 ICP

### 3.1 운영 규모 (상용 TAM/SAM/SOM 대체)

| 계층 | 정의 | 규모 추정 |
|------|------|-----------|
| **전체 범위 (TAM)** | KSLM 인증 검사실 수 × 분야 수 | 검사실 380~450개 × 13분야 = 약 5,000~5,850 검사실-분야 |
| **접근 범위 (SAM)** | 활성 심사 참여 검사실 + 연간 개정대상 문항 | 검사실 380~450개 / 연간 개정 문항 50~120건 / 심사위원 30~50명 |
| **운영 범위 (SOM)** | 실제 시스템 활성 사용자 (연 2~3개월 시즌) | 담당자 2~5명 + 심사위원 30~50명 + 마스터 3~5명 = **35~60명** |

### 3.2 ICP (이상적 사용자 프로파일)

| 속성 | 내용 |
|------|------|
| **기관 유형** | KSLM/LMF 계열 인증심사 운영 기관 |
| **팀 규모** | 문항관리부 2~5명 + 분야별 심사위원 30~50명 |
| **주요 역할** | 문항관리부 담당자 (primary), 분야별 심사위원, 마스터 권한자 |
| **핵심 JTBD** | 심사점검표 정합성을 유지하며 문항을 누락 없이 개정하고 증빙 산출물을 공식 제출 |
| **핵심 고통점** | 공통문항 전파 누락, 수정사유 유실/자동요약, 진행상황 불투명, 잠금 후 우회 위험 |
| **구매 의사결정** | 기관 내 예산 자체 집행 (외부 SaaS 대비 TCO 우위) |
| **성공 지표** | 개정 완료율 100%, 이력 누락 0건, 심사점검표 정합성 100%, 증빙 Export 오류 0건 |

### 3.3 Beachhead 세그먼트 분석 (Geoffrey Moore)

가장 개정 작업량이 많고 공통문항·분야특이 설명이 복잡한 분야를 우선 검증 대상으로 선정한다.

#### 후보 세그먼트 스코어링 (1~5점)

| 세그먼트 | 타는 고통 | 지불 의사 | 점유 가능성 | 추천 잠재력 | 합계 |
|----------|-----------|-----------|-------------|-------------|------|
| **검사실운영** (가장 많은 문항·공통문항 비중) | 5 | 5 | 5 | 4 | **19** |
| **임상화학** (일반+요경검, 분야특이 설명 복잡) | 5 | 5 | 5 | 4 | **19** |
| 진단혈액 (문항 수 보통) | 4 | 5 | 5 | 3 | 17 |
| 수혈의학 | 3 | 5 | 5 | 3 | 16 |
| 임상미생물 | 3 | 4 | 5 | 3 | 15 |

**선정 Beachhead**: **검사실운영 + 임상화학** (동점 공동 1위, 두 분야가 공통문항 전파 + 분야특이 설명 양쪽 시나리오를 모두 커버)

#### 90일 도입 계획 (기관 내 롤아웃 기준)

| 기간 | 활동 |
|------|------|
| D-60~D-45 | 검사실운영·임상화학 담당 심사위원 대상 파일럿 — 화면 A 선정→화면 B 편집→Export 1사이클 실습 |
| D-45~D-30 | 갭 항목 수정(verbatim 분리, 화면 A 영속화) 반영 후 2차 검증 |
| D-30~D-15 | 전 분야 심사위원 온보딩 트레이닝 (역할별 2시간 세션, 마스터 권한자 별도 1시간) |
| D-15~개정 시즌 개시 | 실사용 모니터링, 이슈 핫픽스 |

### 3.4 GTM — 기관 내 롤아웃 전략

**채널**: 기관 내 전산 공문 + 워크숍 발표 + 역할별 온보딩 세션 (외부 채널 불필요)

**메시지 (역할별)**:
- 편집자(담당자): "개정 시즌 내내 공통문항 전파 누락·수정사유 유실 없이 이력을 완전 추적합니다."
- 심사위원: "지난해 문항과 올해 수정안을 색상 강조로 나란히 보면서 클릭 몇 번으로 수정유형을 선택하세요."
- 마스터 권한자: "변경 범위를 한눈에 파악하고, 잠금 해제 시 사유와 감사로그가 자동 기록됩니다."

**성공 지표 (출시 후 1개 개정 시즌 기준)**:
- 개정 완료율 100% (잠금된 문항 수 / 개정대상 문항 수)
- 시스템 내 이력 누락 0건 (revision 로그 non-blocking 수정 후)
- Export 오류(한글 깨짐, 분야 누락) 0건
- 수기/이메일 병행 건수 0건

## 4. 페르소나 3종

### P1. 이수현 — 문항관리부 담당자 (Primary Persona)

| 항목 | 내용 |
|------|------|
| 역할 | 전체 개정 프로세스 조율, 공통문항 일괄 처리, Export·제출 |
| 접속 빈도 | 개정 시즌 중 매일, 시즌 외 월 2~3회 |
| 시스템 역할 | editor (일부 기능 approver 위임) |
| 핵심 JTBD | "전 분야 문항이 심사점검표와 정합하는 최종 파일을 인증 마감일 전에 제출한다" |
| 주요 고통점 | ① 공통문항 일부 분야 전파 누락 → 사후 수작업, ② 수정사유가 화면 B에서 사라지거나 자동요약됨, ③ 진행 상황(분야별 완료율) 실시간 파악 불가 |
| 성공 기준 | 공통문항 전파 누락 0, verbatim 수정사유 Export에 동일 표시, 분야별 진행률 대시보드 |

### P2. 박진우 — 분야별 심사위원 (Secondary Persona)

| 항목 | 내용 |
|------|------|
| 역할 | 담당 분야 문항 내용·설명 수정 제안, 검토 상태 전환 |
| 접속 빈도 | 개정 시즌 집중 (주 3~5회), 시즌 외 거의 없음 |
| 시스템 역할 | editor |
| 연령·배경 | 45~60세 임상교수, PC 친숙도 중간 |
| 핵심 JTBD | "작년 문항과 달라진 점이 무엇인지 확인하고, 필요한 항목만 빠르게 수정한다" |
| 주요 고통점 | ① 전년 대비 색상 강조 비교가 불편, ② 수정유형 선택 항목 의미 모호, ③ 내가 수정한 문항의 처리 상태 불투명 |
| 성공 기준 | 색상 DiffText 1화면, 수정유형 선택지 레이블 명확화, 내 워크리스트 상태 실시간 표시 |

### P3. 최규원 — 마스터 권한자 (Approver·Admin Persona)

| 항목 | 내용 |
|------|------|
| 역할 | 최종 승인·Lock 실행, 신설·삭제 등 민감 작업, unlock 사유 기록 |
| 접속 빈도 | 개정 시즌 월 2~4회 (집중 검토 기간 주 1~2회) |
| 시스템 역할 | approver + admin |
| 핵심 JTBD | "변경 범위를 신속히 파악하고 최종 승인 후 잠금으로 공식화한다. 사후 감사 요청에 즉시 답할 수 있어야 한다" |
| 주요 고통점 | ① 변경된 문항 범위 파악이 어려움, ② 민감 작업(신설·삭제) 실수 위험, ③ 감사 추적 근거 불비 |
| 성공 기준 | 변경 범위 요약 대시보드, 민감 수정유형 approver 전용 잠금, unlock 시 사유 강제 입력 + 감사로그 |

> **보조 언급**: 조회 전용 사용자 (viewer) — 읽기 권한만 있으며 수정 불가. 향후 외부 감사 대응을 위해 역할 테이블에 포함되어 있음.

## 6. Value Proposition

### 고객 직무 (Customer Jobs)

| 유형 | 직무 |
|------|------|
| Functional | 심사점검표 정합성을 유지하며 연간 문항을 개정하고 공식 증빙을 제출한다 |
| Emotional | 개정 작업에 대한 신뢰와 책임소재 명확성 — "내가 수정한 내용이 정확히 기록된다" |
| Social | 개정 결과물이 인증기관 공식 산출물로서 외부 감사를 통과한다 |

### Gain (기대 이익)

- 공통문항 전파 누락 0: 13개 분야 공통문항이 자동으로 동기화
- 연도별 추적 5년 아카이브: 인증갱신 증빙 즉시 Export
- 색상 강조 DiffText: 심사위원이 수정 의도를 한눈에 파악
- Lock+REVISED: 공식본이 시스템 내에 있음을 외부 감사자에게 증명

### Pain (현재 고통)

- 수기·이메일 병행으로 인한 버전 관리 실패
- 수정사유 자동요약 또는 유실 (verbatim 보장 없음)
- 화면 A→B 선택 손실 (새로고침 시)
- 분야별 Export 한글 깨짐 (미검증)
- 공통문항 전파 시 분야특이 설명 덮어쓰기 위험

> 가정: 이 기능이 다음 개정 시즌(2027년) 종료 후 "데이터를 신뢰할 수 없다"는 이유로 사용이 중단되었다. 무엇이 잘못되었는가?

| # | 실패 모드 | 범주 | 가능성 | 영향 | 예방 전략 |
|---|----------|------|:------:|:----:|----------|
| 1 | **verbatim 수정사유 회귀** — 서버 side에서 reason 처리 로직 변경(trim 이상의 변환)으로 저장된 텍스트가 입력과 달라짐 | 데이터 정합성 | 높음 | 심각 | raw_reason 컬럼 분리 + 저장 전 SHA-256 해시 검증 + 회귀 테스트 고정 (TS-01/02) |
| 2 | **공통문항 전파 누락** — 전파 모달을 사용자가 반복 dismiss하거나 전파 API 실패 시 조용히 무시됨 | 신뢰성 | 높음 | 심각 | 전파 실패 시 PATCH 전체 롤백 + 전파 결과 건수 UI 명시 + 전파 누락 알림 배치 검사 |

## 14. Solution 범위 (v1 갭 수정 vs 미래)

### v1 갭 수정 (현 개정 시즌 전 필수 — P0)

우선순위 순서:

1. **revision 로그 non-blocking → blocking 전환** (R-22) — 이력 누락 방지의 기반
2. **verbatim reason raw/display 분리** (R-12) — raw_reason 컬럼 추가, 기존 데이터 마이그레이션
3. **화면 A 선택 서버 영속화 검증** (R-08/R-24) — Worklist 프론트 동기화 확인
4. **unlock 사유 강제 + 감사로그 강제** (R-20) — US-09, TS-04/05
5. **TOCTOU 잠금 체크 원자적 업데이트** (R-23) — findOneAndUpdate 조건부
6. **민감 수정유형 UI 분기** (R-10) — approver 전용 항목 비활성화
7. **공통문항 전파 시 분야특이 설명 보존 검증** (R-29)
8. **Export 한글 폰트 번들 검증** (R-06) — CI 포함

### v1.5 개선 (갭 수정 후 다음 스프린트 — P1)

- verbatim 저장 전 미리보기 UI (R-13)
